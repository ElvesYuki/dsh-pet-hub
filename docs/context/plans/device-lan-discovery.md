# 圆屏局域网发现与恢复

## Spec

维持圆屏发起 VPL1 TCP 的方向。Hub 在显式选择的本机网卡上发布 DNS-SD 服务 `_dsh-pet-hub._tcp.local.`，监听使用该网卡唯一的私网 IPv4。广播仅包含服务名、动态解析的地址与端口，以及发现契约 `version=1`。服务实例名仅用于区分候选，USB 绑定身份、归属、本机配置及密钥不进入广播。发现结果属于不可信地址输入，现有 VPL1 双向认证决定是否接纳会话。

Hub 地址变化时撤下广告、关闭旧监听与设备连接，随后仅监听新地址。接口没有合格地址或有多个合格地址时等待。重连基线、设备 boot 及会话序号约束沿用现有认证适配器，状态和旧动作不能跨网络切换复活。旧固件继续使用固定地址和 USB ARM。USB 查询保留，组播屏蔽时可以通过固定地址和 USB ARM 回退。

## D2 接线约束

1. 初次开通发现继续使用同一 USB 描述符的 Fence 绑定核对。Hub 先持久保存已核对的设备公钥，并关联当前绑定范围。之后由明确的 USB 操作允许设备跨重启使用发现。设备沿用原先保存的 Hub 公钥和当前绑定范围的设备签名密钥。任何中间失败均可用 USB 补做，丢失或不匹配的 pin 保持关闭，禁止从局域网公告或未认证报文恢复信任。
2. 固件仅在 STA 在线、绑定有效、发现已开通且未维护时查询。候选必须位于当前链路的私网 IPv4，按有限批次和带退避的握手逐个核对。只有通过 VPL1 的候选可接入状态与控制。地址或公告实例名变化不改变绑定。撤销、换绑与网络关闭须清除运行期候选和会话，撤销或换绑令旧的持久授权失效。
3. 回退沿用固定地址、原 USB ARM 和 USB 状态读取。关闭发现后停止公告及查找。跨重启保存绑定信任的记录设计与已有 USB 指令的向后兼容需在 D2 的 Spec／Diff 中固定。现场要分开记录 Mac 换地址、圆屏冷启动、同网多个 Hub、组播被拦和只读 USB 回退。

## D2 实施 Spec／Diff

- 已明确配置发现网卡的 Hub 首次启动沿用同一 USB Fence 和 `ARM` 取得板端公钥。Hub 在私有登记目录原子落盘准备记录，再发关联的 `VPCNET1 DISCOVERY <id> ENABLE <device_key_sha256>`。圆屏验证当前绑定及自己已存公钥的摘要，将绑定范围和公钥摘要写入独立 NVS 记录并读回。Host 收到匹配 `enabled` 后持久提交确认记录，冷启动只接受已确认记录。中断后可用同一 USB 重新执行，已存公钥不允许换成不同公钥。
- Hub 侧的准备和确认记录按登记 revision、完整绑定范围和 USB 标识摘要隔离。记录只含公钥及范围摘要，保留现有登记和 Keychain 格式，旧插件仍可读旧索引。未确认记录不可启动 LAN。失效的记录由现有绑定门禁隔离。回退先通过同一描述符的 `VPCNET1 DISCOVERY <id> DISABLE` 清除板端持久许可，再清空 Hub 发现网卡，恢复固定地址和 USB ARM。USB 状态查询始终可用。
- 固件使用固定版本的 Espressif mDNS 组件。只在日常 STA 有 IPv4、许可匹配当前绑定且可播放时查询 `_dsh-pet-hub._tcp.local.`。只尝试该 STA 的同链路 RFC 1918 IPv4，校验唯一的 `version=1` TXT、有效端口和候选去重。一轮最多八个候选依次握手，查询及单个握手有界，耗尽后退避。应用层 VPL1 与播放帧无改动。传统 `ARM` 暂时选固定端点，`DISARM` 停止本次运行，二者保持原持久语义。
- 验证覆盖 USB 请求匹配、准备与确认的写入顺序、中止后重试、绑定变化停用、错误 Hub 候选、公钥替换、多个候选和乱序回执。运行 Hub 回归、固件宿主对拍及 ESP32-S3 交叉编译。发现关闭是日常配置缺省。发布签名、烧录、DSH 换包与真机操作不纳入本轮。

### D2 操作与回退

启用时在测试 profile 保留 `deviceLan` 原端口，明确填写 `discoveryInterface`，并在首次启动连接已绑定的 USB。之后的 TCP 建连继续依赖原 Hub 签名助手可从持久 Keychain 取用对应密钥。日常安装曾使用指向临时旧目录的签名转接，完整 Mac 重启后该原址是否可用仍需单独确认。[日常签名恢复现场记录](wifi-motion-live.md#2026-11-24-现场记录)

回退先停用本 profile 的 Hub，保持 USB 接入，以 `node scripts/device-enrollment.mjs discovery-disable "$ENROLLMENT_DIR"` 撤销板端发现与本地确认。再恢复空的 `discoveryInterface` 和旧固定地址，保留原端口及绑定，重新启用 Hub。若先恢复维护窗口的固定地址 ARM，设备本次运行会采用该地址，跨重启的发现许可仍由 `discovery-disable` 管理。回退到旧 Hub 包仍可使用原登记索引。

### 现场对照与修复设计

以原 `0.1.43` 同一 boot 复测。首次认证心跳 5.45 秒，同端口重载 5.86 秒。换临时端口后 Mac 独立浏览看到旧实例移除、新实例加入，并确认新 SRV 端口、`version=1` 和正确 IPv4。47 秒内圆屏查询完成数增加 2，候选、TCP 和认证计数均未增加。同期看到 ESP 发 PTR 查询，Mac 两次发出包含完整四类记录的响应，顺序为 PTR、A、TXT、SRV。首次发现时被观察到的完整公告则在 SRV 后携带 A。原诊断只给出计数，未在圆屏抓取原始 DNS 字节。

锁定的 Espressif mDNS 组件在 PTR 查询中立即尝试按 hostname 归并 A，该 hostname 在处理 SRV 时才填入。因此合法的 A 在 SRV 前出现时可丢失。修复在仅含有效 STA、TTL、版本、SRV 主机及端口而缺 IPv4 的结果上，按 SRV 主机名补发 A 查询。保留最多两次补查、每次 600 毫秒，正常已有 IPv4 的快路径不增加查询。补查只接纳同一 STA、有效 TTL、有效同网段 IPv4，当前路由与绑定失效时丢弃结果。使用 SDK 查询接口，保留 Bonjour 声明、USB 诊断格式和 VPL1 认证。宿主回归模拟 SDK 给出 SRV／TXT 完整但缺 A 的结果，并覆盖补查限额、过期、错网卡、错地址及取消。
