# 已绑定圆屏的 USB 换钥匙

## Spec

Hub 在独立、长期的私有登记目录用新助手生成不可导出的 P-256 密钥。换钥匙前先用新助手做一次随机挑战验签，并把新目标、epoch 与 Keychain 引用写成 `pending`。保留原目录、密钥及 Hub profile。沿用显式选定的 USB 身份、独占串口以及现有 Fence 核对。圆屏保留 device、controller、binding，提交时只换公钥并将 epoch 加一。Wi-Fi、天气、素材和分区使用原存储。

固件在绑定、USB 连接且空闲时才签发单次 challenge。`BINDKEY 1` 的 COMMIT 同时携带旧私钥授权和新私钥准备证明。两个签名用不同的固定域，覆盖旧绑定身份、epoch、当前 boot、challenge 引用号、随机 nonce 和新公钥。固件验证两条签名后先排空旧 LAN 控制，再提交并逐字节读取 NVS；未验证的请求保持原控制和记录。成功时上一 epoch 的发现许可失效。既有首绑和固定 ARM 接口继续可用。

Hub 只有收到绑定完整 digest 的新 Fence 后才确认本地 `bound`。旧板无能力或设备拒绝时保留原绑定。提交回执缺失时，下次通过 USB 核对当前记录。读回旧绑定可以使用同一个新密钥重新请求，读回新绑定则补做本地确认，任何第三种记录停止处理。已有确认只做复验。设备提交后，旧目录仍可保留作证据，恢复旧密钥需要由当前新密钥再授权一次换钥匙，不能把回写旧记录当作回退。

## Diff 与验收

| 模块 | 变更与证据 |
| --- | --- |
| 固件绑定、USB | 扩展既有 challenge/NVS 状态机，独立版本字段和请求关联。离线验证错误旧签名、错误新签名、重放、超时与持久读回。 |
| Hub Keychain、登记 CLI | 新助手可在私有长期目录初始化。显式 `prepare-signer` 和 `rotate-key` 预配、换钥匙及断点恢复。使用同一串口校验，不改变正在运行的配置。 |
| 互操作 | 使用独立临时文件、模拟 USB、真实 C++ 对端及合成 macOS Keychain。交叉编译生成未签名候选。 |

现场开始前停用旧 Hub，先备份登记和签名助手，核对设备操作窗口与回退固件。仅在新索引确认为 `bound` 并用新助手做成 USB Fence 后切换 Hub 目录；若启用发现则对新 epoch 重做 USB 开通。Mac 和圆屏重启后再核对 TCP。源码实现和离线验证阶段不改本机日常 profile、不连接板、不烧录。

## 现场入口

旧 Hub 仍可签名且圆屏已运行支持候选时，记录一次新的长期目录。之后每次重试使用这两个相同的目录。只有 CLI 报告新绑定核对成功后，才以新目录替换 `deviceEnrollment.enrollmentDirectory`。若回退到支持当前登记目录格式的 Hub 版，继续使用新目录。未部署新版协议时，Hub 不发送换钥匙写请求。

```sh
NEW_ENROLLMENT="$(node scripts/device-enrollment.mjs prepare-signer)"
node scripts/device-enrollment.mjs rotate-key "$OLD_ENROLLMENT" "$NEW_ENROLLMENT"
node scripts/device-enrollment.mjs keychain-verify "$NEW_ENROLLMENT"
```

如遇提交结果未知，保持两个私有目录不变，恢复 USB 后重新执行 `rotate-key`。若 NVS 暂时不可读，先正常重启圆屏再读取。设备已提交时，重跑只核对新绑定并补确认。需要保留旧助手作为历史凭据时继续保护该目录，旧公钥已不能签入新的绑定 epoch。

## 离线验收（2026-11-24）

- Node／C++ 使用实际固件绑定状态机核对旧签名、新签名分别错误、challenge 超时和重放拒绝，以及成功提交后回执丢失、设备重启、再次读取绑定并补确认。恢复时不调用旧签名器。已绑定设备的能力查询新增换钥匙位，旧首绑响应字节向量保持一致。
- 用合成 Keychain 验证新助手在长期私有目录生成密钥，新进程打开同一目录后实际签名通过。系统 Keychain 搜索列表保持一致。
- `npm run check` 通过；`npm test` 共 2145 项，2133 通过、12 跳过。USB 专项共 19 项，18 通过，1 项因未配置外部向量路径跳过。日常 DSH `0.2.2-rc.5` 目标候选只在本地构建产出。

- 实体 USB、实板换钥匙、Mac 和圆屏整机冷启动、日常 Hub 切换，以及旧 epoch 在真机 LAN 上的撤销均待现场验收。

## 真机部署顺序

1. 核对本机两份回退镜像的固定摘要和原台架签名。用同一台架签名给本次候选生成仅供该圆屏使用的本地镜像，单独保留原构建输出。先用已登记 USB 身份读取当前版本、槽位与维护标志，并用原助手做一次本机验签。
2. 优先走设备自身的双槽 OTA。`0.1.40` 的 `OTA2` 需要由操作者在本机输入临时联网凭据。现有管理端可信发布入口只接受正式三段版本；本次带测试后缀的镜像需要单板维护入口。若走 ROM 直接写入，则单独核准写入窗口，只允许待启用应用槽及对应的新选择记录，预先读取验证应用槽与分区表并保留原活动应用和选择记录。
3. 首次启动按 USB 状态确认新版本和槽位，先用旧索引证明原绑定仍能读回。旧 Hub 暂停后备份当前配置、索引和原签名助手，才进行换钥匙。新公钥已确认后，日常 Hub 使用新索引并重新开通发现，联动保留原设置。设备重启和 Mac 整机重启分别验收；在用户方便中断 Mac 上的工作时执行整机重启。
4. 在换钥匙前遇到固件故障，先回到原活动槽并检查原绑定。换钥匙之后先保留新登记并核对设备状态；需要恢复旧密钥时，走新密钥签名授权的反向轮换。

### 真机预检（2026-11-24）

- 通过日常设备页同款的独占 USB `STATUS3` 从已登记圆屏读回 `0.1.40-l-battery-usb-pair-test`／`ota_1`，无维护任务或待重启升级，查询后释放串口。原 Hub 索引与旧助手通过本机随机挑战验签。
- 本机 `0.1.40` 和 `0.1.39` 的签名镜像匹配原报告中的 SHA-256，并通过原台架公钥验签。未签名 `0.1.42` 的 SHA-256 与构建记录一致，构建分区表与两个回退版本一致。预检未读取设备完整应用槽。
- 自动审批因缺少明确的私有固件签名授权拒绝签名命令。候选仍未签名，日常 DSH 配置、应用槽和绑定保持预检前状态。

- 单板维护脚本已离线校验三份签名镜像及启动选择序列 33。写入前需核对并备份两个应用槽和原选择记录，只放行 `ota_0` 和选择 `ota_0` 的单个扇区。首启需确认新版本、完整待机片段和原绑定。
- 首次现场尝试停在只读预检，系统显示日常 DSH 持有圆屏串口。应用槽与启动选择未写入。

### 圆屏上板与首启验收（2026-11-24）

- 用户拔插同一条 USB 数据线后，原固件状态读回及 ROM 握手恢复。核对真机分区表、两个完整应用槽的摘要和原 OTA 选择记录，备份并同步落盘。仅写 `ota_0` 和对应的一个选择扇区。候选槽及选择记录写后读回，`ota_1` 和其他受保护 Flash 区域在首启前的摘要一致。
- `0.1.42-k-battery-usb-pair-test` 从 `ota_0` 启动并确认，OTA 选择序列为 33。真机待机完整播放 241 帧，20.841 FPS，零丢帧。原 `0.1.40`／`ota_1` 留板作回退，`0.1.39` 的原备用槽镜像留本机备份。
- USB 状态读回新版本和槽位。圆屏已声明支持换钥匙，使用原日常登记的完整绑定执行 USB Fence 已通过。此轮只部署固件，尚未提交公钥变更和开通发现。
- 刷写期间临时停用日常 Hub。Mac 解锁后在原窗口恢复 Hub `0.0.8`，插件详情显示运行中。设备页显示 `0.1.42-k-battery-usb-pair-test`、TCP 实时状态、已从设备核对持久绑定及联动关闭。日常配置文件与操作前备份逐字节一致。

### 真机换钥匙（2026-11-24）

- 备份日常 profile 与原登记、原助手。新助手在长期私有目录独立生成密钥，本机新旧签名验证均通过。
- 在登记圆屏通过 USB 认可双签名并完成绑定读回，设备、控制者和绑定标识保留，epoch 加一。新索引提交后独立验签通过。日常 Hub 切换新索引，在原固定地址恢复认证 TCP 和心跳，下阶段发现回退使用此配置。旧助手保留作历史备份，运行链路已切到新助手。
