# VP8 BOOT 持久绑定确认

适用于明确启用 `VP8_BOOT_PAIRING` 的双槽 OTA 候选。直连 USB 下的主机仍须先核对设备身份。`0.1.4` 没有此扩展。文本命令 `STATUS2` 及原维护接口沿用。`VP8PAIR1 <base64>\n` 输入和 `@VP8_PAIR1 <base64>\n` 输出均承载一个 PBP1 v1 帧，使用规范标准 Base64 填充。数据损坏、错方向、非法保留位、超长、截断或附加字节整帧丢弃。PBP1 v1 的帧头、LE 长度和 CRC32 沿用。现有 USB 行缓冲上限不变。

能力探测为类型 6，回复 129 的能力字节置 bit 2。类型 7 只接受 `operation=1` 的首绑挑战，回复 130。类型 8 的签名、设备身份和新代数校验沿用历史代码。类型 132 仅表示提议进入物理等待，回显本次 reference。等待窗口使用现有至多 15 秒的限制，按钮只在显示确认提示的 DMA 完成后采样。

## 新鲜持久回执

类型 10 请求，正文 64 字节，LE 整数。

| 偏移 | 字段 |
|---:|---|
| 0 | 0 为 poll，1 为 fence |
| 1–3 | 保留，零 |
| 4–11 | 设备本次 boot ID |
| 12–27 | 设备 ID |
| 28–59 | 主机本次生成的 32 字节非零随机数 |
| 60–63 | poll 为本次接受的非零 reference，fence 为零 |

类型 133 响应，正文 136 字节，LE 整数。

| 偏移 | 字段 |
|---:|---|
| 0 | 结果 0 正常、1 拒绝、2 忙、3 超时、4 存储错误 |
| 1 | 状态 0 未绑定、1 等待、2 已绑定、3 存储错误 |
| 2–3 | 本次模式，保留零 |
| 4–27 | 当前 boot ID、设备 ID |
| 28–35 | 已读回记录的代数。没有记录时为零 |
| 36–67 | 已提交 controller ID、binding ID |
| 68–99 | 已提交公钥的完整 SHA-256 |
| 100–135 | 请求随机数和 reference |

poll 仅在本次 boot 接受过对应提议时应答。等待状态的身份字段来自已持久记录，未写入的提议没有资格填充这些字段。短按提交到现有 NVS 分区的 `vp8_binding/record`，只有读回与写入字节一致才成为 `Ok/Bound`。历史 PBP1 的 `pet_binding/record` 保留。写入或读回异常返回存储错误。USB 失联或设备重启后旧 reference 失效。

fence 在空闲时先撤销当前挑战和待确认窗口，再返回同一个请求关联下的持久状态。主机使用本次 boot、设备、模式、nonce、reference 加上下文和精确身份元组进行核对。只在 `Ok/Bound` 且 controller、binding、代数、公钥完整摘要均匹配时记为已绑定。只有新鲜 `Ok/Unbound` 的 fence 回执可清除未知意图。其余结果可在后续直接 USB 会话对账。此扩展不创建 PMA1 租用。逻辑会话关闭无法保证设备立即发现 USB 物理断开，因此使用 fence 明确撤销。

## 显式直连登记

单独启用 `VP8_USB_ENROLL` 时，类型 129／132 的能力位额外置 bit 3。明确选中该 USB 设备且用户点击绑定后，宿主才能发类型 7 操作 3。类型 130 仍为 40 B，正文第 1 字节回显 3。类型 8 的签名输入、正文及 CRC 沿用原 Enroll 格式；仅同一个操作 3 挑战引用可以直接保存，旧操作 1 仍需 BOOT。类型 132 原样回显 reference，成功时 phase 为 2 且代数为新提交值。宿主应发新鲜 type 10 fence，以 type 133 的完整已读回记录结束登记。重插或重启后只发类型 6 和 10。管理端应显式告知该策略依赖直连 Mac 的本地访问控制。[直连 Spec](../../context/plans/vp8-usb-enroll-spec.md)
